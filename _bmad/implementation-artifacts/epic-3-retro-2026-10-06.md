### A. Cross-story defects (the boundaries no single story saw)

**F1. A stop on a run with background subagents live wedges the card, and says the user's own stop "failed". Disposition: fix, before this build is used on a real skill.**
`foldTurn` returns `failed-while-pending` for a failed `result` while background tasks are live (`src/main/fold/turn-end.ts:62-67`, re-checked). `foldFrame` computes `stopped` only for `signal.kind === 'ended'` (`src/main/session-registry.ts:184`, re-checked), so for `failed-while-pending` it says `turn failed · <subtype>` and raises `turn:failed` on the persona (`:187-190`) and never calls `endRun`. `stopRun` has already returned `'ok'`; a second press returns `'ok'` and writes nothing (`src/main/session-stop.ts:63-65`), and an *acknowledged* interrupt has no deadline for the result that must follow (`:69-79`). Result: the card stays `running` with an inert stop control, and the transcript shows a failure for something the user did. If a later background-wake `result` is not an error, `stopped` is false (it requires `signal.failed`) and the run the user stopped ends `run:finished`, `saved · N sections`, green. Same root: if the CLI ends an interrupted turn with a non-error `result`, the stop reads as finished (edge-case lens, `session-registry.ts:184`).
This is not exotic. `bmad-prd` runs spawn research subagents (`judgement-3-1-the-beat.md` §2); `fixtures/runs/fast-path-sonnet.jsonl` carries 12 `background_tasks_changed` frames while `interrupt-inband` carries none. Story 3.7 deferred it as `medium (unverified)` (`spec-3-7-…md` frontmatter) and story 3.8 left it "out of scope" with `deferred: []`; it is in neither `deferred-work.md` nor `sprint-status.yaml`. No test drives a stop through a live background task: `background_tasks_changed` count is 0 in `session-stop.test.ts` and `tests/stop-replay.test.ts` (verification-gap lens, recon-b). The behavior check could not exercise it (the stub carries no tasks).
Corroborated by all three lenses, both reconciliation agents and my own re-read; not observed live. Prevention: a deferral that names an "unmeasured" failure of a headline control is not closed by being written down — measure it in the story that builds the control, or do not mark that story done.

**F3. A run with no streamed `Write` (Edit-only, or Bash heredocs) has no subject, and the card states falsehoods. Disposition: fix.**
`subjectOf` needs `written > 0`, i.e. a streamed `Write`. An `Edit` of a file the run never wrote has no buffer, so `patched` returns undefined and the commit carries no sections (`src/main/fold/route-frame.ts:226-240,278-286`). The card then holds `deadAir = running && !hasText` (`src/renderer/ui/chat/run-card.tsx:122`, re-checked) and prints the fixed string `0 words on disk · autosave on` (`:146`, re-checked, a constant, not read from disk) for the whole run, and finishes `saved · just now · 0 sections`, while the notification for the same run says `finished` (`run-status.ts:87,112` vs `windows/run-notification.ts:70-80`). Opus writes through Bash heredocs (`judgement-3-1-the-beat.md` §3 limit 2; `fast-path-opus`, `coaching-path`), so those runs show notes only under that foot. Reported by recon-a, adversarial #4/#5, edge-case #4, verification-gap #4; story 3.12's matrix names the row and its fixtures README says "still open". Not exercised in the behavior check (the stub's recordings all `Write`). The card's one rule — "a view of the running skill, never a claim about disk" — is broken in both directions.

**F4. The head's `§N` means three different things live, after reload, and at the end. Disposition: fix.**
Live, the head counts by first-seen order; terminal heads and a reload rebuild by document order (`prose-store.ts:196-206` `seed()`). **Observed** in the behavior check (D2): after a mid-document insert, the live head read `revising · §11 Success Metrics`, then the stopped head read `stopped · §11 Open Questions`. **Reproduced** by recon-a with a scratch script over the real prose store: Write of Vision, Goals, Risks, then an applied Edit inserting Success Metrics before Risks gives live `{revising: true, Success Metrics, n: 4}` and, after `seed()`, `{revising: false, Risks, n: 4}`, with Risks renumbered from §3 to §4. That breaks the AC "a section the user has seen is never renumbered" and drops `revising` on reload; the rail's annotation keeps first-seen order, so head and rail can disagree. `tests/run-card-parity.test.ts` compares card fields, not head words, and `prose-store.test.ts:245` pins the reload behavior as correct. Specs 3.3 and 3.6 name it as a residual risk. Root cause is structural: three parallel per-path folds (A2).

**F5. A rail row keeps `stopped` with no card to explain it. Disposition: fix.**
A stopped or failed run's paths read `stopped` with no expiry or clearing event (`src/main/fold/rail-annotations.ts:181-199`; `projections/rail-annotator.ts:68-74`). `endConversation` clears `service.runs` but nothing resets `service.annotations` (`src/main/session-bridge.ts:364-371`), so ending the conversation mid-run leaves `stopped` beside the persona on the rail until a later run writes that file. Reported independently by edge-case #7/#8, adversarial #2, verification-gap #5 and recon-b; no test searched covers conversation end for annotations.

**F6. The 3.13 note-versus-live gate has a zero-margin window and keys on the wrong thing. Disposition: fix, and a live check.**
The grace is `now − runEndedAt ≤ SETTLE_MS` with `SETTLE_MS = 400` (`persona-state.ts:131-137`, `rail-rows.ts:20`), the same constant the rail uses to flip `changing` to `saved`. If the watcher's last observation lands after the terminal event, the flip falls outside the window and the run's own write raises `note` (adversarial #6, edge-case #13, recon-a). The gate also keys on the row's class owner and on "any session running", not on who wrote the file: a human or terminal edit of any file A owns is swallowed for the whole of A's run, and a run by A that writes a file B owns raises `note` on B's tile while the 3.6 annotation names A (adversarial #7, recon-a; the 3.13 design notes call the second deliberate). A chat turn's own write still raises `note` (spec-3-13 deferral, still open). **Observed once** in the behavior check (D5): John's tile read `file changed` instead of `live` about 30 s after a run finished unfocused; not reproduced in four later attempts. This is the judgement's must-change item 3, so a single unexplained recurrence matters.

**F7. Notes: delivery, attribution and a known limit. Disposition: fix.**
`observeMemlog` advances `memlogs.counts` before checking that a single run is in flight, so entries observed after the terminal event, or while two runs are in flight, are consumed and never delivered (`src/main/session-run.ts:259-276`; adversarial #8, edge-case #9). `isMemlog` accepts any `.memlog.md` under `_bmad/` with no owner check, so another persona's or an outside writer's memlog is attributed to the only in-flight run, and a concern-scan line can pull sections into the wrong plan (adversarial #9). With two runs in flight neither card gets notes, so the collapsed line never shows a reason: judgement known limit 5, still open and unowned, and exactly the case 3.5 and 3.9 exist for (recon-a).

**F8. A rejected `Write` leaves its text in the buffer. Disposition: fix.**
A `Write` streams into `docs[path]` at its first character; if the tool then rejects it, `commitResults` records `ok:false` but never restores the prior text (`route-frame.ts:221-228,263-270`). A later applied `Edit` is patched against text that was never written, and the card and rail show sections not on disk (edge-case #6, adversarial #14).

**F9. Persistence: unbounded, shallowly validated, and wrong across windows. Disposition: fix the validation now, defer the rest.**
(a) `isStoredRun` checks that `documents` and `notes` are arrays but not their elements (`src/main/sources/persistence/transcript-file.ts:101-118`); a `documents: [null]` passes and throws in `hydrate` (`conversation-state.ts:298-311`, `prose-store.ts:196`). (b) Every run event rewrites the whole file including every card's full document text on a 500 ms debounce, and cards are dropped only on `clear()` (`projections/transcript.ts:222-251`; adversarial #12, edge-case #15): the main-thread synchronous write grows with the project's whole run history. (c) `storedRuns()` maps every `running` card through `deadOf`, so a second window of the same project is handed another window's live run as failed (`transcript.ts:252`; adversarial #3, edge-case #14).

**F10. Small parser and race defects. Disposition: fix as one batch.**

**F13. The click that raises the window and reveals the card may never fire. Disposition: Sherif's manual check, then fix if confirmed.**
`posted` is a local in `told` and the click closure captures `window`, `sender` and `runId`, not `posted` (`src/main/windows/run-notification.ts:126-134`, re-checked); nothing retains the object. Raised independently by the 3.10 spec's own deferral, recon-b, the adversarial and edge-case lenses; no one could observe the actual behavior, and the behavior check emitted `click` on a patched `Notification` rather than waiting for a real banner. FR94 (activation raises the window and scrolls to the card) depends on it.
