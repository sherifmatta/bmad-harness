### Defects at story boundaries (diff-scope review and behavior check)

**F1. A persona's seat shows no live dot until a run has finished. Medium to high. Fix now.** Main raises a persona's `live` state in one place only: `service.personas.attach(...)` at the end of a run that finished (`src/main/session-run.ts:259`, inside the `run:finished` branch; the header comment at `session-run.ts:45` says the same). A run starts only from a menu dispatch. Opening a persona from its tile or `@name` and talking to it starts none. Observed in the built app (behavior step 5): Mary then John opened from the rail, with a plain reply and a typed round trip, left both tiles `idle`; both turned `live` only after a skill-row button was pressed on each. Story 7.4's own spec says the opposite: "live is raised by `personas.attach` when a session's process is ready" (`spec-7-4-…md:58`) and its acceptance reads "Given a live seat, then its tile shows the existing `live` dot" (`spec-7-4-…md:77`); the epic context defines the dot as "holds context" (`epic-7-context.md`, UX section). The spec's read-only evidence was wrong about the producer, so no test caught it. What does hold, observed: Mary's process kept running after John's `close session`, and John's close wrote exactly one line. [Lesson: a story whose acceptance is a visible mark must assert it through the real path that raises the mark, not through a hand-built `attach`, and its Evidence line must cite the producer by reading it.]

**F2. `/bmad-party-mode <words>` sends the words into a room whose activation turn is still in flight. Medium. Fix now.** A first message that opens the room returns `rest` (`src/main/session-bridge.ts:285-293`); the window then calls `conversation.sendToRoom(outcome.rest)` with no gate (`src/renderer/ui/app.tsx:286-289`). A fresh session starts `busy` (`src/main/fold/turn-end.ts:34`), so `writableSession` answers BUSY (`session-bridge.ts:350`) and `interruptedRoom` interrupts the party skill's own opening turn, or, if the CLI has not acknowledged in time, refuses the send and the words come back to the room composer after the New session chat was already spent (`app.tsx:271-272`). A persona seat does not have this problem: its `rest` queues behind the activation turn. No test combines a first-message open with an immediate room send (`app.test.tsx:3419-3427` and `session-bridge.test.ts:2878-2893` each stop on one side). Not exercised in the behavior check (no Party run). [Lesson: a spec that adds a second way into an existing session kind must name what the new path does with the turn already in flight.]

**F3. The skill header's one button swaps from `Stop` to `close session`, and closing a skill session deletes its thread. Medium. Fix now.** `src/renderer/ui/chat/chat-header.tsx:~107-110` renders `onClick={stops ? onStop : onClose}`. When the turn ends between the press and the click, a second press lands on `close session`, and `closeSession` then calls `removeListedSkillSession`, which removes the session's records, stored run cards and list item (`src/main/session-bridge.ts:589-591`, `:602`). No confirmation. For a persona the same swap only ends a seat and keeps the transcript, so it is harmless there; for a skill session it is the only copy. [Lesson: when a control's identity changes with state and one identity is destructive, the spec says whether the two are separate controls.]

**F4. Focus does not return to a Board opener when the main window is on another view. Medium. Fix now.** `returnFocus` calls `openers.current.get(path)?.focus()` (`src/renderer/ui/board/board-view.tsx:62-64`) while the Board section is `hidden` when the view is not `board` (`src/renderer/ui/shell/shell.tsx:416`, `.view[hidden]` in `shell.css:188`), so the call is a no-op and nothing retries when the Board is shown again. Story 7.1's audit asserts focus return only with the Board mounted visible (`tests/board-audit.dom.test.tsx:546-559`). Read, not run (jsdom cannot show it and the behavior check did not drive close-from-another-view).

**F5. The `/` list (7.3) and first-message resolution (7.5) do not share one rule for what a skill name is. Medium. Fix now.**
- The list narrows case-insensitively (`src/renderer/ui/skills/slash-query.ts:39`); main matches exactly and case-sensitively (`src/main/session-bridge.ts:273-276`), so typing `/BMAD-build x` shows rows and is then refused `no skill named BMAD-build`.
- `foldSkills` lists any non-empty manifest name (`src/main/fold/skills.ts:25-28`); main starts a session only for a name that passes `skillOf` and is one whitespace-free word (`session-bridge.ts:274`). A listed name with a space or an odd character can never start.
- `Enter` always chooses the current row, which is the first prefix match, even when the text already is a complete name (`src/renderer/ui/skills/use-slash-list.ts:96,112`); a full name followed by Enter is rewritten and not sent, and with a longer sibling listed first it is replaced by the sibling. On this install's manifest `bmad-build` precedes `bmad-build-auto`, so it costs a second Enter rather than a wrong skill (behavior step 2 observed the order).
[Lesson: 7.5's design notes record the resolver's rule; 7.3 had already shipped the list. Two stories on both sides of one boundary need one predicate in one file.]

**F6. The first-message roster branch skips the agent-id gate. Low. Fix now.** `openFirst` calls `openSeat(ctx, sender, projectRoot, name)` for any roster id that matched a manifest name (`session-bridge.ts:281`); the tile path rejects the same id through `isAgentId` (`session-bridge.ts:320`), and the cast path checks it too (`:183`). A roster id with `.` (allowed by `SAFE_AGENT_ID`, `sources/install/schema.ts:32`) cannot be opened from its tile but can be from `/<id>`. The id comes from the user's own install, so the exposure is small; the gate's stated rule is that nothing else may through.

**F7. Queued messages are dropped differently for a skill session and a persona. Low. Defer.** A persona keeps what the user typed when its process exits on its own and drops it only on `closed` (`src/renderer/ui/chat/conversation-state.ts:851-855`); `skillClosed` drops it for any reason (`src/renderer/ui/chat/skill-session-state.ts:56`). Two stories apply opposite rules to one event and no line says the text was dropped.

**F8. A skill's streamed deltas join only when the transcript's last entry is the same session, so two streams shred the stored thread. Low. Defer.** `src/main/fold/transcript.ts:51` joins on `last`; with two skill sessions or a skill and a persona streaming at once each delta becomes its own `skill` record. The live view is whole (the renderer joins by session) and a persona has the same property today (`transcript.ts:59-61`), so this is copied rather than introduced. After a reload the thread would read as many one-word turns.

**F9. `initialsOf` splits a surrogate pair and yields an empty disc for a blank name. Low. Defer.** `src/renderer/ui/persona/initials.tsx:50` uses `word.slice(0, 1)`. After 7.7 the disc is the only identity device, so a name that starts with an emoji or a non-BMP letter draws a lone surrogate, and an empty name draws a blank disc.

**F10. The dead handoff path now carries other announcements under its old name. Low. Defer (extends 7.4's own deferral).** `onHandoff` still announces room and skill refusals (`src/renderer/ui/chat/use-conversation.ts:256,467`), while `app.tsx:106-111` says it is reachable only through a reply that carries a handoff and main no longer writes one. The next person who deletes "dead handoff code" per that comment removes the screen-reader announcement of those refusals.

**F11. Stale test assertions left as found. Low. Defer.** `.portrait` in `src/renderer/ui/party/epic-4-audit.dom.test.tsx:350` matches nothing, so its assertions pass trivially; the `handed to Ada` fixture at `src/renderer/ui/chat/negative-surface.test.tsx:89` names a line main no longer writes (`spec-7-6-…md` deferred list). Both were left by a spec that forbade editing existing assertions.
