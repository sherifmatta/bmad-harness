## Intent

**Problem:** The roster is spelled out by hand in `app.tsx` (`PREVIEW_CAST`, with a comment naming this story as the one that removes it), and nothing reads a BMad install. Until the team and each persona's menu come from the project's own resolvers — bounded, validated, degrading to last good with a named error — every later surface (preflight, tiles, chat header, skill buttons) would be built on a hardcode.

**Approach:** A main-side install source runs BMad's own resolvers through `uv`, validates every answer by hand-written schema, and hands a projection that keeps the last good roster and last good menu per agent; a coalescing watcher re-resolves on config change; one snapshot per refresh crosses two new preload methods to a renderer hook, and `app.tsx` mounts the resolved roster in place of `PREVIEW_CAST`. `skill`-versus-`prompt` lives only in main.

## Boundaries & Constraints

**Always:**
- **Configuration comes only from the resolvers, run as subprocesses.** `resolve_config.py --key agents` for the roster; `resolve_customization.py --skill <root>/.claude/skills/<agentId> --project-root <root> --key agent.menu` for each menu. No code path reads `config.toml` or `customize.toml`, none parses TOML, and no dependency is added to do so (FR3, AD-8).
- **Every invocation is timeout-bounded and its output validated before use** (FR4). Three failure classes — invocation failure (spawn error, non-zero exit, output over the buffer), timeout, and *valid JSON in an unexpected shape* (or not JSON at all) — share **one** degrade path: keep the last good result, surface a named error, and never emit an empty roster without one.
- **Error codes are stable and the envelope is exact:** `{ code, message, detail? }`, codes `resolver/invocation-failed`, `resolver/timeout`, `resolver/unexpected-shape`, `menu/entry-malformed`, `install/no-project`, `install/unexpected`. `message` is harness register (lower case, mono, `·`-separated, no terminal punctuation, facts not guidance). `detail` is built by the harness from a closed vocabulary (`exit 1`, `signal SIGTERM`, `spawn ENOENT`, `output was not json`, or a dotted validation path such as `agents.bmad-agent-pm.name · expected a non-empty string`) — **never subprocess stderr, never a stack trace, never a configuration file path** (FR91, UX-DR31).
- **The roster carries exactly six fields per agent** — `module`, `team`, `name`, `title`, `icon`, `description` — plus the agent id (the `[agents.<id>]` key) as its identity, in the resolver's key order (`EXPERIENCE.md:177`: order as resolved). `team` is optional (`EXPERIENCE.md:177`, "where present"); the other five are required strings, with `module`, `name` and `title` non-empty. Unknown fields (`identity`, `communication_style`, …) are dropped, not forwarded (AD-10).
- **Roster validation is all-or-nothing.** One invalid entry rejects the whole answer as `unexpected-shape` and the last good roster stays — the alternative is a roster silently missing a colleague. **Menu resolution is per agent**: one agent's failed menu never wipes another's.
- **The agent id is untrusted project content** and is the only thing composed into a filesystem path. It must match `^[A-Za-z0-9][A-Za-z0-9._-]*$` and not contain `..` or the roster is `unexpected-shape` with `detail: agents · unsafe agent id` — checked before any per-field rule, and never echoed, so a hostile id cannot reach `detail`; the skill directory is `<root>/.claude/skills/<agentId>`, composed by id, never found by globbing (FR2).
- **The renderer receives `{ code, description }` per menu entry and nothing else.** The `skill`-versus-`prompt` decision and its value are stored in the projection keyed by `agentId` then `code`, reachable only through a main-side lookup that Epic 2's `menu.dispatch` will call (AD-3, AD-9). No `skill` or `prompt` key, and no skill name, appears in any snapshot.
- **A menu entry needs `code` and `description` and exactly one non-empty string of `skill` or `prompt`.** A malformed entry is dropped from the menu and named — `menu · <Name> · entry <CODE> has neither skill nor prompt` (or `has both skill and prompt`, `has no description`; `entry <n> has no code` where the code itself is missing) — one error per entry, `detail` the agent id (AD-9, `EXPERIENCE.md:266`).
- **A resolve that returns valid JSON with no `agents` key, or `agents: {}`, is a valid empty roster** — TOML with no `[agents.*]` tables has no agents. It yields `agents: []` and **no error**; the message that names it is Story 1.8's, which triggers on exactly `agents.length === 0 && errors.length === 0`. Likewise an absent `agent.menu` key is a valid empty menu.
- **One refresh, one snapshot, one emission.** Roster and all menus resolve, then a single snapshot with a monotonic `revision` is emitted, and only when the renderer-visible content changed. The renderer applies it in one `setState` — one frame — and never animates arrival or removal (FR5, `EXPERIENCE.md:265`).
- **The watcher coalesces.** Events inside one burst (default 400ms, injectable) trigger one refresh; a change arriving during a refresh triggers exactly one more after it. The watched set is stat-independent and path-shaped: `_bmad/config.toml`, `_bmad/config.user.toml`, any `_bmad/custom/*.toml`, and `.claude/skills/<any>/customize.toml`. Everything else under `_bmad/` (the artifacts the rail will watch) is ignored so their churn never re-resolves anything.
- **The harness writes nothing into the project.** Resolvers run with `PYTHONDONTWRITEBYTECODE=1` from a neutral working directory (`os.tmpdir()`, injectable), through `uv run --no-project --quiet`.
- **Layering holds:** `src/shared/install.ts` is types only; sources know nothing of the projection; the projection imports sources, never windows, renderer or preload; the preload imports only `import type` from shared; nothing under `src/renderer/` reaches `src/main/`.

**Never:**
- Never read `config.toml`/`customize.toml` (not even "just to check it exists"), never parse TOML, never implement layering, never add a dependency — `chokidar` (pinned, already a dependency) is the only new import.
- Never discover agents by globbing a skills directory or by a name prefix. Never read `_bmad/_config/skill-manifest.csv` (its `path` column names `_bmad/bmm/agents/…`, which does not exist on this install).
- Never forward raw stderr, an `Error` message, a stack, or a `.toml` path across the bridge, into `message`, or into `detail`.
- Never invoke `resolve_party.py` (no Epic 1 consumer; Story 4.1's), never dispatch a menu entry, never open or touch a session — there is none, and re-resolution takes no session dependency (FR5).
- Never build the preflight message for no agents, `claude`/`uv` checks (1.8), the persona tile, the rail head, the shell or the live-region mount (1.9/1.10), or the rail's watcher (1.11) — this story's watcher is its own and shares nothing with it.
- Never render `icon` as a portrait; the roster carries it, no surface uses it yet.
- No spinner, skeleton or loading sentence for the pending state — the window renders nothing until the first snapshot, exactly as it does for the project path today.
- Never the CSS word for the focus stroke anywhere under `src/`, comments included (`tests/accessibility.test.ts:304`); no `aria-live`, no `role="alert"`, no arrow-key literal, no `style={{ }}` literal, no motion, no shadow, no new z-index, no new token.
- Never widen `HarnessApi` beyond `getProjectPath`, `getInstall`, `onInstallChanged` — no `invoke(channel, …)`, no `ipcRenderer` in reach.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Live roster | this repo's `resolve_config.py --key agents` | five agents in resolver order, six fields + id each | No error expected |
| Live menu | `bmad-agent-analyst` | ten entries keyed by code (`BP`,`MR`,`DR`,`TR`,`TS`,`CR`,`UV`,`CB`,`WB`,`PC`); `BP`,`CB`,`WB`,`PC` held as `skill`, `MR`,`DR`,`TR`,`TS`,`CR`,`UV` as `prompt`; snapshot carries `code` + `description` only | No error expected |
| Resolver exits non-zero | runner reports exit 1 | last good kept (or `agents: []` if none), `resolver/invocation-failed`, `detail: exit 1` | Named error; stderr dropped |
| Resolver times out | child outlives `timeoutMs` and is killed | last good kept, `resolver/timeout` | Named error; child killed, not leaked |
| `uv` absent | spawn `ENOENT` | `resolver/invocation-failed`, `detail: spawn ENOENT` | Named error; 1.8 owns the friendly message |
| Not JSON | stdout `garbage` | `resolver/unexpected-shape`, `detail: output was not json` | Last good kept |
| JSON, wrong shape | `agents` is an array; an entry lacks `name`; `team` is a number | `resolver/unexpected-shape`, `detail` the failing dotted path | Last good kept; whole roster rejected |
| Unsafe agent id | `[agents."../../x"]` | `unexpected-shape`, `detail: agents · unsafe agent id` (the id is not echoed) | No path is composed; no process spawned for it |
| Empty roster, valid | `{}` or `{"agents":{}}` | `agents: []`, `errors: []` | None — Story 1.8's trigger |
| Malformed entry | menu entry with neither / both / no description / no code | entry dropped, one `menu/entry-malformed` naming agent + code + what is missing | Other entries stay |
| Menu resolver fails, roster fine | `resolve_customization` exit 1 for one agent | that agent keeps its last good menu (or `[]`), one `resolver/invocation-failed` naming it | Other agents unaffected |
| Roster shrinks | an agent vanishes from the resolved config | its tile data, menu and main-side dispatch entries drop from the snapshot | No session exists to touch |
| Change burst | config rewritten (atomic rename) then appended within 400ms | exactly one refresh, exactly one emission | — |
| Change during refresh | file changes while a resolve is in flight | that refresh completes, then exactly one more runs | — |
| No visible change | refresh produces an identical renderer view | no emission, `revision` unchanged | — |
| Stale push | renderer receives `revision` 4 after 5 | 4 is ignored | — |
| Unknown window | `install:get` from a webContents with no project | `{ ok: false, error: { code: 'install/no-project', … } }`; preload rejects with the envelope | Named error |

## Tasks & Acceptance

## Design Notes

**Why the skill directory is composed, not found.** FR2 and AD-10 forbid *discovering* agents by globbing skill directories on a name prefix, because that hardcodes BMad's layout. Composing `.claude/skills/<agentId>` from an id the resolver already handed over is a different act: the id **is** the skill's name (AD-18 sends `/<agentId>` as the first turn, and the session resolves it from exactly that directory), so nothing is being inferred about layout that the product does not already depend on. The alternative — the manifest's `path` column — is a file the harness has no contract with and which is wrong on this install. Treat this as the one path-shaped assumption in the story, and the reason the id is validated before it becomes part of a path.

**Why an absent `agents` key is an empty roster, not an error.** `--key` omits keys it cannot find, so a project whose merged config has no `[agents.*]` tables gets `{}` back — indistinguishable at the wire from "the key was there and empty", and semantically the same: there are no agents. Calling it `unexpected-shape` would make the case Story 1.8 exists to explain (a correctly installed BMad that resolves none) surface as a resolver *fault*. The rule that keeps FR4 honest is that emptiness is only ever *silent* when it is a **failure** result — which always carries an error — and an empty result with no error is a positive fact 1.8 turns into its four-part message. Its trigger is stated in the matrix so 1.8 does not have to rediscover it.

**Why the roster is all-or-nothing and menus are not.** A roster is one answer about one set, and the failure FR4 names is "a garbage roster silently": accepting the valid entries of a partly-wrong answer is exactly a roster silently missing someone. A menu is a *per-persona* answer, and the failure that matters there is a whole team losing buttons because one skill's `customize.toml` is broken — so its failure and last-good are per agent, and an individually malformed entry is dropped and named rather than voiding its neighbours.

**Why one emission, and only when it differs.** "Update in a single frame" is a renderer claim, but it is produced in main: a snapshot is assembled after roster *and* every menu have resolved, so the renderer can never draw a new roster over old menus. Suppressing an identical snapshot matters because the watcher is deliberately broad (any `customize.toml` under any skill fires it) and most changes are to skills that are not agents; without the comparison, every one is a re-render with nothing new in it.

**Why the bridge builds its service lazily, per sender.** AD-7 puts install state in main and makes the renderer a pure projection that a reload loses nothing from — so the natural owner is the window's project, and the natural trigger is the renderer asking. Eager construction at window creation is the alternative, and it is ruled out by the suite as it stands: three files drive the real launch path against a stub window and would start spawning `uv`. Lazy creation costs nothing at runtime — the renderer asks on mount — and a reload finds the projection already warm.

**The envelope for `install:get` specifically.** The existing `getProjectPath` throws a plain `Error` at an unknown window, and Electron flattens that to a string. FR91 covers *every* failure crossing the bridge, and this is the first channel that can fail in a way the user reads, so it returns a discriminated reply and the preload turns `{ ok: false }` into a rejection carrying the envelope object. `getProjectPath` is left as it is: it is a launch-time programming error with no user-facing path, and reworking it is a change to a story that is done.

**What is deliberately left for later.** The polite announcement of resolver errors (`EXPERIENCE.md:512`) needs the live region mounted, which Story 1.9 owns (`deferred-work.md`); the error line's real placement at the rail head of the Team half (`EXPERIENCE.md:264`, an `[ASSUMPTION]`) is 1.10's; `uv` being on `PATH` when the app is launched from the Dock rather than a terminal — GUI apps on macOS inherit a minimal `PATH` that omits `/opt/homebrew/bin` — is exactly what Story 1.8's preflight names, and an unresolvable `uv` here is a `spawn ENOENT` named error, never a blank. Diagnostics go to `process.stderr` as the launch errors already do; `userData` logging (Conventions) has no home yet and is not invented here. The one-window-per-project index still keys on the raw path string (`deferred-work.md`), so the install service inherits that identity.
