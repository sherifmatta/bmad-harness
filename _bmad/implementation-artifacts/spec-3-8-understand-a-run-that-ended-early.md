## Intent

**Problem:** A run that ended early tells the user nothing about how far it got. The card head says the bare word `stopped` or `failed`; the rail row loses its annotation entirely the moment the run ends (`fold/rail-annotations.ts:133-140` deletes the run); and no test has ever driven `interrupt-sigint` or `reviewer-gate-failure-induced` to a terminal event, so the classification rules the epic states — terminal state from the per-turn `result`, `is_error` plus `subtype`, never `stop_reason`, never the exit code; a write counting on `tool_result`; one `doc:committed` per tool call — hold only by construction and can regress silently.

**Approach:** The terminal head names the section reached, read from the card's last *confirmed* write and never from the streamed text. The rail keeps a stopped run in the annotation table instead of deleting it, so its rows read `stopped` while their disk state stays the watcher's. Everything else the story asks for is already built: the three terminal fixtures are replayed end to end through the real bridge, and the invariants are pinned by guards, so the claim can fail.

## Boundaries & Constraints

**Always:**
- A terminal card's head reads `stopped` or `failed`, and `stopped · §N <Name>` / `failed · §N <Name>` when the run has a confirmed write of the card's subject. `<Name>` is the last name of `RunCardDocument.sections` for the subject path and `N` is its 1-based place in that same array — the sections of that path's last confirmed write (`conversation.ts:99-105`). The streamed `ProseStore.progress` / `seen` are never read for a terminal head: a section announced by prose but never confirmed by a `tool_result` is not a section reached, so a run interrupted mid-`Write` with nothing confirmed reads the bare word.
- `§` stays spelled in `src/shared/section-progress.ts` and `src/renderer/ui/chat/run-status.ts` only, and the terminal word is one shared definition so the head and the rail cannot disagree, as `progressLabel` already is for `writing`/`revising`.
- The polite lifecycle announcement follows the head: `<name> · stopped · §N <Name>` and `<name> · failed · §N <Name>`, the bare form with nothing confirmed. The gate stays the same four events in the same order.
- `run:stopped` and `run:failed` keep their run in the annotation table, marked stopped, and every path it still showed annotates `stopped` — one word, no section, no count, no denominator, and the owner it already carried. `run:finished` drops the run as it does today. A stopped run's held text is released when it is marked (the table holds text only to place an `Edit`), so a terminal run costs its path names and nothing more.
- The rail's two channels stay apart: a stopped annotation never creates, removes or reorders a row, never touches `disk`, and never moves a row to `saved`. A later run writing the same path replaces the annotation, as it does today.
- Terminal state is read from the per-turn `result` row: `is_error: true` means stopped (the run's stop was asked for) or failed, with `subtype` carried as the failure's `detail` and in the harness's `turn failed · <subtype>` line; `stop_reason` is read nowhere in `src/`; no run or turn ends on a process exit code. `error_during_execution`, `error_max_budget_usd` and any other error subtype travel the same path.
- A write counts on its `tool_result`: exactly one `doc:committed` per tool call carrying that call's id, `ok: false` committing no sections and naming the rejected call, so a rejected batch never appeared in the foot and nothing un-renders.
- When the session ends with the run, the transcript's last word is the harness's own (`harness:said`), never a persona's: main synthesises no `persona:said`.

**Never:**
- No new contract event, command, channel, preload method or `RunStatus` member; no field added to `RunStopped`, `RunFinished` or `RunFailed`; no change to `CONTRACT_VERSION`.
- No error text on the persona tile, no new word in `STATE_TEXT`, no separate dot state for stopped versus failed (both stay `error`).
- No section, count, denominator, owner guess or contention wording in the stopped annotation (contention is Story 3.9); no new annotation vocabulary beyond the one word.
- No foot on a terminal card, no dead-air phrase, no pinning, no collapsed line for a terminal run, no spinner, badge, toast, sound, retry, resume, revert or restore control.
- No new harness line, no copy change to `LINES`, no reclassification of a subtype into harness vocabulary, and nothing of the CLI's text beyond the subtype word already validated.
- No live run and no network in any test: the three fixtures are the evidence.

## Design Notes

- **Confirmed, not announced, is the whole point of the AC.** The card already holds both: `RunCardDocument.sections` is set only by an `ok` `doc:committed` (`fold/run-card.ts:95-103`), while `ProseStore.progress` is settled from streamed text and survives the terminal event. A run interrupted mid-`Write` has prose showing §7 and nothing committed; naming §7 would be the failure this story exists to prevent, so the terminal head reads the card's `documents` and the streamed store is not consulted at all.
- **The rail keeps the run instead of growing a second table.** Marking the run and releasing its text is a smaller change than a parallel structure, keeps `annotationsOf`'s "later-started run wins" rule for free, and bounds what a terminal run costs to its path names. The one word is shared with the head's vocabulary so the guard that keeps `writing`/`revising` in one file keeps this one there too.
- **Most of the story is already built, and that is the risk.** AD-11/AD-18 classification, commit-on-`tool_result`, one commit per call, the rejected-call envelope and the tile's wordless `error` all exist; what has never existed is a test driving `interrupt-sigint` or `reviewer-gate-failure-induced` to a terminal event — every `error_max_budget_usd` assertion in the repo today is over hand-built frames. The replay and the guards are the deliverable for those clauses, not new code.
- **The gate fixture's shape is load-bearing.** Its two `result/success` rows at 906 and 940 fall while background tasks are live, so `foldTurn` returns no signal and the run is still in flight; the task set empties at 945 and the failure at 950 ends it once. Replaying a prefix that stops before 945 would instead exercise `failed-while-pending`, which is 3.7's deferred entry and stays out of scope.
