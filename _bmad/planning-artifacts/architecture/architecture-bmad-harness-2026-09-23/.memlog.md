- (version) Verified 2026-09-23: Electron 44.4.4 stable (Chromium 152, Node 24; released 2026-09-22, supported to 2027-03-02). Tauri 2.11.5 (2026-07-01). Electron majors ship every 8 weeks, latest three supported.
- (decision) USER: Electron 44 is the shell. Rejected Tauri 2.11 and local-server+PWA after full comparison. Reasoning: all three reach every capability and share one shape (privileged Node/Rust process owns disk+runs, web view renders) so this is mostly a transport+packaging choice. Electron wins because the project's entire risk is UI iteration (does the room read as colleagues or as a chat box with a portrait glued on) and Electron keeps 100% of the iteration budget in that layer; its native workload here (spawn, JSONL parse, fs watch, TOML read, multi-window) is trivial Node. Tauri's size/RAM/start wins are real but land on axes this product is not judged on, and are noise beside the claude subprocesses the harness itself spawns; its cost is Rust in the highest-churn module (stream interpretation) where the user has no debugging fluency. Local-server+browser was ruled out on two grounds: a weaker sense of 'a room you go to' (a browser tab is literally the ChatGPT form factor the spec names as the failure mode) and a localhost HTTP server able to spawn skill runs with project write access is an exposure Electron IPC does not carry.
- (constraint) Rejected alternative recorded for the record: Tauri + Node sidecar. Carries both runtimes, forfeits the size win, and adds a process boundary to the fiddliest code. Not to be revisited without new reason.
- (decision) Stream interpretation lives in the main process only. Main folds raw stream-json into a domain event vocabulary (run:started, doc:section-opened, doc:prose, doc:section-committed, persona:said, run:stopped); the renderer never sees Claude Code wire format. Prevents two interpreters (card epic and rail epic) disagreeing about the current section, and confines a Claude Code format change to one module.
- (decision) USER: run recording is a day-one invariant, not optional. Every run writes its raw stream-json to a run log and the interpreter is a PURE FOLD over that sequence - no I/O, no wall clock, no filesystem. Mitigation for the 12-minute feedback loop on the highest-churn module: real runs become replayable fixtures (fast-path single 68KB write, coaching-path batched writes, SIGINT mid-write, failure in the reviewer gate) testable offline in milliseconds. Also gives CAP-12 a forensic trail.
- (decision) Two truth channels never merge. A rail row exists, and claims content, ONLY because the filesystem watcher saw the file. The run stream may annotate a row with run-scoped metadata (owning persona, section in flight, stopped) but may never create a row, remove one, or assert what a file contains. An announced write that never lands produces no row. Implements no-second-source-of-truth literally and closes the tool_use-vs-tool_result trap by construction.
- (decision) The live document card is strictly run-scoped: born with a run, dies with it, never a cache of project state.
- (decision) Run lifecycle settled: one claude subprocess per skill invocation, alive across that skill's elicitation loop, exiting on completion. No idle subprocesses are held between runs. A finished session costs no process, no lock, no memory.
- (decision) CAP-8 continuity mechanism: cross-persona context is carried by the PROJECT ARTIFACTS on disk, not by inheriting token context between subprocesses. BMad is memlog-then-derive, so a persona's conclusions (including concessions won in argument) are already in PRD.md / .memlog.md when the next run reads them. CAP-8's 'no handoff presents as a restart' is satisfied by unbroken scrollback plus artifacts, not by transplanting context.
- (decision) USER: main process owns the conversation transcript and persists it per project, keyed by project path, under Electron userData. Renderer is a pure projection holding nothing durable, so a reload is free. Answers SPEC open question 1 (session history across launches) rather than deferring it.
- (decision) The harness writes NOTHING into the user's project. Everything under _bmad/ got there because a skill run wrote it. Harness bookkeeping (transcripts, run logs, caches) lives in Electron userData. Protects the outputs rail from showing harness state as if it were a project artifact.
- (decision) USER: an explicit end/new-session control exists, distinct from CAP-11's stop-a-run. Required once transcripts persist, otherwise a project's scrollback only grows with no in-product reset. Extends the spec's control surface.
- (version) Verified 2026-09-23: React 19.3 (released 2026-09-09; View Transitions and Fragment Refs now stable). Electron Forge is the official toolchain but its Vite support is still marked experimental as of Forge 7.5.0.
- (decision) Build tooling: electron-vite + electron-builder, not Electron Forge. Routine call, flagged to the user: Forge is official and all-in-one but its Vite integration is still experimental as of 7.5.0.
- (decision) USER: React 19.3 renders the UI. Rejected Svelte 5 (better fit for streaming by default, less code, but not the user's daily language and this project cannot afford iteration-speed loss) and the no-framework lift of the mockup's imperative renderers (fine for two views, painful for the conversation surface, which is the part that actually grows).
- (decision) USER: the mockup's :root token block and component CSS are lifted VERBATIM as the stylesheet of record. No component hardcodes a colour or a dimension; everything reads a token. Prevents the party cast and the persona tiles - separate epics rendering the same face at different sizes - drifting to 'roughly the same dark grey', which is how a deliberately restrained UI stops looking deliberate.
- (decision) Portraits are pure functions with no I/O and no external assets: portrait(artParams, size) -> SVG string lifted from the mockup, plus artParamsFor(agentId) -> artParams for agents installed after v1 (CAP-10). Determinism is unit-testable: the same agent id must yield the same face on every machine.
- (decision) Prose deltas never pass through component state one at a time. ~5,795 input_json_delta events land for a single document write; per-delta re-render janks the app during the exact moment the product is being judged. Main coalesces; the card commits to one node on an animation frame.
- (constraint) SPEC CORRECTION (bmad-install-contract.md): a [[agent.menu]] entry carries exactly one of skill OR prompt, not always skill. Verified in the real install - 6 of Mary's 10 entries are prompt-style (deep-recon with a type pre-selected). A harness dispatching only skill leaves 60% of the Business Analyst's buttons dead: a direct CAP-4 failure. Dispatch must handle both: skill -> /<skill-name>, prompt -> that text as the run's opening turn.
- (constraint) SPEC CORRECTION (bmad-install-contract.md): the authoritative registry of installed agents is _bmad/config.toml [agents.*] (name, title, icon, description, module, team), not the per-agent customize.toml. The contract names only customize.toml, so a harness built to it could only enumerate agents by globbing skill directories on a name prefix - a hardcode of the kind the spec forbids. customize.toml supplies identity, communication_style and the menu; config.toml supplies who exists.
- (decision) USER: the harness resolves effective agent configuration by CALLING BMad's own resolver scripts (resolve_customization.py, resolve_config.py) and using the merged JSON. customize.toml is not the effective config - BMad layers _bmad/custom/config.toml and config.user.toml over it with non-trivial merge rules (scalars override, arrays append, arrays-of-tables merge by code/id). Reading the raw file shows wrong buttons to any user who customized a menu. Reimplementing the merge in Node was rejected as exactly the model-of-how-BMad-works the spec constraint forbids growing; the resolver-with-Node-fallback variant was rejected because the fallback is the copy that rots unnoticed. Accepted cost: runtime dependency on uv + Python 3.11, which every BMad install already requires.
- (decision) The install is watched, not read once: _bmad/config.toml and the agent customize.toml files are re-resolved on change. Nearly free given the watcher already exists, and CAP-1's promise that adding an agent surfaces it reads better without a relaunch. Routine call, flagged to the user.
- (decision) SPEC open question 2 (concurrent writers to _bmad/) CLOSED: it dissolves under the harness-writes-nothing invariant. The harness has no write to lose, so another tool overwriting a file mid-run is not a conflict it must arbitrate - the filesystem arbitrates, last writer wins, as between any two editors. The rail reports what disk says and is correct by construction; the card is run-scoped and never claimed to describe the project. THE HARNESS REPORTS, IT DOES NOT ARBITRATE. No locking scheme.
- (decision) USER (overrode my recommendation of one-run-per-window, correctly): concurrency is ONE RUN PER PERSONA. Evidence I had underweighted - ui-surfaces.md defines the state vocabulary PER PERSONA TILE, so a five-state per-tile vocabulary only makes sense if personas can be independently busy; one-run-per-window would leave only one tile able to go amber. It also serves the thesis better (a room where the team visibly works) and is not autonomy, since the user pressed every button. Same persona, two runs: still forbidden. Write-collision risk is carried by BMad's own disjoint artifact ownership (John: PRD/epics/sprint-status; Mary: research/briefs; Winston: architecture; Amelia: code) and, where it does collide, by the report-not-arbitrate rule.
- (decision) USER: with concurrent runs, live document cards are conversation entries in time order. The ACTIVE persona's card renders full (streaming prose, current section, elapsed, stop). A run belonging to a non-active persona COLLAPSES to a single live line carrying real state (persona - writing - SSN - elapsed - stop), expanding on persona switch or click. Never a spinner, and the reading surface stays calm. Closes a gap neither SPEC.md nor the mockup addressed.
- (decision) USER: macOS only, personal/dev build. No code signing, no notarization, no auto-update, no cross-platform shell escapes, no installer matrix. The whole operational dimension reduces to a launch preflight; budget stays on the UI where the risk is.
- (decision) Launch preflight is required: the harness verifies claude is on PATH and authenticated, and uv + Python 3.11 are present, and names precisely what is missing and how to fix it. CAP-1 promises zero CONFIGURATION, not zero PREREQUISITES; without this the harness opens to an empty room with no personas and no explanation, which reads as broken rather than unconfigured.
- (constraint) Verified: bmad-party-mode SKILL.md specifies turns as '{icon} **{name}:**' back to back - a documented convention, so speaker attribution and lighting the current speaker are a parse of main-thread text_delta. resolve_party.py supplies the roster and slots into the resolver decision (AD on calling BMad's own scripts).
- (gap) CAP-9's side panel (open disagreements with parties/status/substance/age, decisions so far) has NO DATA SOURCE. bmad-party-mode emits prose and is explicitly instructed 'Never work in a summary or takeaways'. Every escape hits a constraint: harness-side inference grows the model the spec forbids; a classifier pass is the same objection plus cost; customising the skill via _bmad/custom/ is sanctioned but makes the harness require an install customisation and changes behaviour for terminal users too.
- (decision) USER: defer the party side panel. Party mode v1 ships the room - chosen cast, permanently visible faces, lit speaker, no turn-taking gate, summary written to _bmad/. The disagreement/decision tracker is deferred with a revisit condition. CAP-9's success criterion is therefore NOT fully met as written and SPEC.md needs amending to match.

- (event) Reconcile pass (3 parallel subagents vs SPEC.md, vs execution-model.md+install-contract, vs ui-surfaces.md+mockup+scope-tiers) returned ~37 findings. Token VALUES in AD-14 all verified correct against the mockup.
- (decision) USER (after reconcile surfaced the root cause): the run model changes from ONE SUBPROCESS PER SKILL to ONE LIVE SESSION PER PERSONA. Activating a persona spawns claude -p '/bmad-agent-<x>' --input-format stream-json, alive while the user works with that persona; chat turns AND skill invocations are both turns into that session. Root cause it fixes: three independent capability gaps had one origin - CAP-2 'the user holds a conversation' had no home because every path to the subprocess was a skill run; CAP-3's identity/communication_style had no persona to animate between runs; CAP-12's 'persona states what failed and offers to resume' had no living speaker, so the harness would have had to compose it in the persona's name, which is exactly the fake personhood the spec calls a trust liability. It also matches BMad's real model: bmad-agent-pm IS a skill and [[agent.menu]] is the menu it presents once activated. Costs accepted: execution-model.md's literal claude -p '/<skill-name>' invocation needs amending; persona sessions are long-lived so processes persist while in use (superseding the earlier 'a finished session costs nothing'); context accumulates across skills in a session (good for CAP-8, costly on a long day); and SIGINT must halt a SKILL without killing the SESSION - unverified by the spike, which measured killing the process.
- (gap) OPEN RISK carried into the build: stop semantics under the persona-session model. CAP-11 requires halting a run in progress; the spike measured SIGINT killing the subprocess (rc=0 in ~250ms) but never tested interrupting one turn of a live --input-format stream-json session without ending it. If it cannot be done, stopping a skill costs the persona session and CAP-8 continuity within that session.
- (event) Reviewer gate: lint clean; rubric walker + adversarial lens returned. Adversarial found 18 compliant-but-incompatible builder pairs, 3 critical. Root cause: AD-3 fixed an event VOCABULARY and the spine treated that as a CONTRACT.
- (decision) AD-3 rewritten from a vocabulary into a contract: events out AND commands in, each declared once in src/shared with an explicit payload type and a stated cardinality, contract version stamped on every persisted log. Menu entries resolve in MAIN (renderer sends a code, never a resolved skill name, which would go stale on re-resolution). Identity keys fixed: sessionId is primary for session scope, runId for run scope, agentId says which agent a session activated and MAY BE ABSENT (party = room-owned). Routing rules added so the same bytes are never rendered twice or lost: main-thread text_delta outside a tool call is persona:said; prose inside a write is doc:prose from input_json_delta; .memlog.md writes are run:note and NEVER doc:prose (otherwise memlog text poisons the document section parser permanently).
- (decision) Turns within a session are strictly SERIALISED. At most one turn in flight per session; anything typed during a run is queued and sent when that turn completes. Closes the critical hole where a chat turn mid-run produces a result row that fold/run reads as the run finishing - killing the card and re-enabling buttons mid-write. A RUN is now defined: a turn dispatched from a menu entry, bounded by run:started and a terminal run event; a plain chat turn is not a run and raises no card.
- (decision) doc:committed cardinality fixed at exactly ONE PER TOOL CALL, carrying the call id and the list of sections committed - never fanned out per section. Without this the card epic and the rail epic each pick a different cardinality and a Fast-path 15-section single write shows 'SS1 of 9' for 8.5 minutes. Edit vs Write handling separated: Write replaces the buffer and may open sections, Edit patches and is a revision that never advances the counter (20 of 21 observed writes were revision Edits).
- (decision) Rail row carries two independent fields never written by both sources: disk-derived state (absent/changing/saved) owned by the watcher, and an optional run-derived annotation (owner, section, stopped) owned by the stream. No shared field, so no precedence question - closes last-writer-wins on the exact CAP-12 stop case.
- (constraint) AD-18 invocation CORRECTED against the installed CLI: --input-format is only valid with --print, so the form is 'claude -p --input-format stream-json --output-format stream-json --include-partial-messages --verbose --setting-sources project,local' with /bmad-agent-<x> sent as the FIRST TURN ON STDIN, not as a positional prompt. Also: a result row arrives PER TURN, not once per process; process exit code is not the signal because a session outlives every turn in it.
- (constraint) Trust boundary stated explicitly (it was self-contradictory): the project's CODE is trusted - its skills and _bmad/scripts resolvers are exactly what the user already executes when running BMad, and the harness runs them with no more privilege. The project's CONTENT is untrusted the moment it is rendered, because it is largely model-authored. Resolvers additionally get a timeout and a defined failure path (degrade to last good, surface a named error, never a silent empty roster).
