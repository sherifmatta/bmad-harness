- (decision) USER: Electron 44 is the shell. Rejected Tauri 2.11 and local-server+PWA after full comparison. Reasoning: all three reach every capability and share one shape (privileged Node/Rust process owns disk+runs, web view renders) so this is mostly a transport+packaging choice. Electron wins because the project's entire risk is UI iteration (does the room read as colleagues or as a chat box with a portrait glued on) and Electron keeps 100% of the iteration budget in that layer; its native workload here (spawn, JSONL parse, fs watch, TOML read, multi-window) is trivial Node. Tauri's size/RAM/start wins are real but land on axes this product is not judged on, and are noise beside the claude subprocesses the harness itself spawns; its cost is Rust in the highest-churn module (stream interpretation) where the user has no debugging fluency. Local-server+browser was ruled out on two grounds: a weaker sense of 'a room you go to' (a browser tab is literally the ChatGPT form factor the spec names as the failure mode) and a localhost HTTP server able to spawn skill runs with project write access is an exposure Electron IPC does not carry.
- (constraint) Rejected alternative recorded for the record: Tauri + Node sidecar. Carries both runtimes, forfeits the size win, and adds a process boundary to the fiddliest code. Not to be revisited without new reason.
- (decision) Stream interpretation lives in the main process only. Main folds raw stream-json into a domain event vocabulary (run:started, doc:section-opened, doc:prose, doc:section-committed, persona:said, run:stopped); the renderer never sees Claude Code wire format. Prevents two interpreters (card epic and rail epic) disagreeing about the current section, and confines a Claude Code format change to one module.
- (decision) USER: run recording is a day-one invariant, not optional. Every run writes its raw stream-json to a run log and the interpreter is a PURE FOLD over that sequence - no I/O, no wall clock, no filesystem. Mitigation for the 12-minute feedback loop on the highest-churn module: real runs become replayable fixtures (fast-path single 68KB write, coaching-path batched writes, SIGINT mid-write, failure in the reviewer gate) testable offline in milliseconds. Also gives CAP-12 a forensic trail.
- (decision) Two truth channels never merge. A rail row exists, and claims content, ONLY because the filesystem watcher saw the file. The run stream may annotate a row with run-scoped metadata (owning persona, section in flight, stopped) but may never create a row, remove one, or assert what a file contains. An announced write that never lands produces no row. Implements no-second-source-of-truth literally and closes the tool_use-vs-tool_result trap by construction.
- (decision) The live document card is strictly run-scoped: born with a run, dies with it, never a cache of project state.
- (decision) Run lifecycle settled: one claude subprocess per skill invocation, alive across that skill's elicitation loop, exiting on completion. No idle subprocesses are held between runs. A finished session costs no process, no lock, no memory.

- (decision) USER (after reconcile surfaced the root cause): the run model changes from ONE SUBPROCESS PER SKILL to ONE LIVE SESSION PER PERSONA. - (decision) AD-22 NEW. Tool steps are ONE new main-folded event, run:step, keyed by callId; payload is a union: {status:'running', label} then {status:'done'|'failed'} (both with runId, sessionId, callId, at). Cardinality: inside a run, exactly one 'running' per main-thread tool call and then exactly one 'done' or 'failed'; a call whose result never comes is closed on the card by the run's terminal event, with no extra event. Chat turns (no runId) emit none. Calls aimed at .memlog.md emit none (that text is run:note, AD-3); a document Write/Edit DOES emit a step beside its doc:* events, the shared callId joins them. 'running' is raised when the call's input finishes streaming (content_block_stop), because that is when the tool is executing and the label is whole; duration = result instant minus that instant, both injected ctx.now (AD-4). Parallel calls share one result frame so their durations are approximate; accepted. Binds CAP-5, CAP-11, CAP-12. Prevents a step list with no real source (AD-20), two renderers deriving different labels, raw tool input reaching the renderer.
- (decision) AD-22 label rule: derived in main, in a pure fold module, from a closed table of tool name -> verb plus ONE allow-listed input field (file_path -> project-relative path, outside the project -> basename only; Skill -> skill name; Task -> subagent_type; WebFetch -> host only; Bash -> program name only, never arguments or the raw command; Grep/Glob/WebSearch -> verb only; unknown tool -> its own name, charset-limited). Control chars stripped, length capped (about 48 chars, paths truncated from the left). The fold holds only the decoded target field (bounded buffer) and never forwards input. The UX example 'read story 5.6' is NOT derivable without the harness inventing words; label is verb plus path (read design/tokens.css).
